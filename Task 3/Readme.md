# Решение

Синхронные обмены данными между `ins-product-aggregator`, `core-app` и `ins-comp-settlement` следует заменить на события в Apache Kafka.

- `ins-product-aggregator` продолжает получать данные из API страховых компаний и публикует события об изменении продуктов и тарифов.
- `core-app` и `ins-comp-settlement` независимо читают эти события и обновляют свои локальные проекции
- `core-app` публикует события об оформленных, измененных и отмененных страховках, а `ins-comp-settlement` строит по ним собственный реестр.

Для надежной публикации событий применяется Transactional Outbox. Данные и запись сохраняются одной транзакцией PostgreSQL, после чего отдельный воркер публикует событие в Кафку.

# Проблемы и риски текущей архитектуры

| Проблема или риск | Последствие при подключении еще пяти компаний | Решение |
|---|---|---|
| Синхронный запрос из ins-product-aggregator во все страховые компании | Время ответа определяется самым медленным API. Рост с 5 до 10 интеграций повышает вероятность таймаута и частичного отказа | Независимый сбор данных с ограничениями времени, повторами и circuit breaker. Распространение готового каталога через Kafka |
| core-app обновляет каталог раз в 15 минут | Пользователь видит устаревший тариф до 15 минут, а сбой очередного запроса увеличивает отставание | События ProductUpserted и ProductRemoved, которые обновляют локальную копию сразу после успешного получения данных |
| ins-comp-settlement получает каталог только раз в сутки | Расчет может использовать устаревшие условия продукта | Постоянное использование product-catalog.v1 |
| ins-comp-settlement раз в сутки выгружает все оформленные страховки из core-app | Большой единократный запрос создает всплеск нагрузки | Поток событий всех оформлений и инкрементальное построение реестра |
| Ошибка одного внешнего API влияет на общий синхронный запрос | Недоступность одной компании ухудшает работу всех | Изоляция интеграций  и отдельные повторы для каждого источника |
| Повторная доставка и изменение порядка событий | Повторная обработка может создать дубли, а старое событие затереть новое состояние | Семантика at least once, ключ партиции по productId или policyId |

# Transactional Outbox

Transactional Outbox используется в двух местах:

- в core-app для атомарной записи страховки и события PolicyIssued
- в ins-product-aggregator для атомарного обновления каталога и события об изменении продукта.

Воркер читает новые записи через периодический `SELECT ... FOR UPDATE SKIP LOCKED`. После успешной публикации запись удаляется.

# Контракты событий

Минимальный envelope:

```json
{
  "eventId": "uuid",
  "eventType": "PolicyIssued",
  "eventVersion": 1,
  "aggregateId": "policy-id",
  "aggregateVersion": 3,
  "occurredAt": "2026-08-18T10:15:30Z",
  "producer": "core-app",
  "correlationId": "uuid",
  "payload": {}
}
```

Основные топики:

| Тема | Ключ | Производитель | Потребители | 
|---|---|---|---|
| product-catalog.v1 | productId | ins-product-aggregator | core-app, ins-comp-settlement |
| policy-events.v1 | policyId | core-app | ins-comp-settlement |
